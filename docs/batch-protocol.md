# Batch protocol contract

- Policy: the Market authority initializes one immutable `batch-policy` PDA with a 30–60 second window and 60–300 second lock lifetime. The setup defaults are 45 and 120 seconds. A policy change requires a new version and migration review rather than altering live window identity.
- Identity: `batch` PDA with seeds `batch`, little-endian `u16` version 1, Market key, and little-endian `i64` window start. The start is the Euclidean floor of the chain timestamp to the policy duration. The window is `[start, start + duration)`.
- Lock deadline: `window_end + policy.lock_seconds` in chain time. A Batch can lock once, after the window end and before its lock deadline. The lock deadline cannot be extended. Requests must predate the window end, remain active and unexpired through the lock deadline, and have exact remaining quote in isolated Token-2022 escrow.
- Set: at most four request public keys, strictly ascending by decoded 32-byte key. The coordinator takes the first four verified eligible keys in that order; later keys remain available for later windows. The program stores the full selected keys and rejects duplicate, out-of-order, or oversized sets. The lock instruction supplies matching request/escrow account pairs. The SDK's four-pair legacy transaction fixture serializes to 641 bytes, below the 1232-byte limit. A four-request local validator lock simulated at 16,923 compute units on Solana 3.1.10 with the SBF v2 artifact.
- Deployment: build the IDL with Anchor, then compile the program for SBF v2 before deploying with the upgradeable loader. The default Anchor SBF v3 artifact was rejected by that loader; SBF v0 deployed but hit an existing Buy Request stack limit during local simulation.
- Expiry: after the lock deadline, any caller can transition the Batch to expired and clear every corresponding request lock with the complete stored set. A request's owner actions remain locked until this cleanup. No seller opening is required or published to release the set.
- Buyer priority: maximum premium descending, creation slot ascending, decoded request key ascending. Non-partial buyers are skipped when their entire remaining quantity would exceed the Stage remainder. Accepted winners consume the minimum of their remaining quantity and Stage remainder. The last accepted buyer's maximum premium is the uniform marginal premium. A proposal requires exact full Stage coverage; one raw unit short fails.
- Seller priority: minimum premium ascending, Plan creation time ascending, decoded Plan key ascending. Future settlement must replay these priorities and all allocation checks onchain.
- Quote affordability: no reference quote is committed at this stage, so a structurally covered proposal is pending until a signed Pyth reference permits exact checked integer charge verification. A proposal never authorizes movement of stock or quote.
- No-match: hidden Stage terms cannot produce a public onchain absence proof. A Batch with insufficient private demand expires honestly; no unproven `NO_MATCH` claim is emitted.
